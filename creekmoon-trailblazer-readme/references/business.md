# 业务项目 README 规范

适用：后台/中台、业务服务、有业务主线的应用、多模块业务聚合工程。  
读者：开发接手。目标：**3 分钟建立心智模型，10 分钟知道从哪里接手。**

返回 [`SKILL.md`](../SKILL.md) 完成场景判定后阅读本文。

## 业务子类型（只影响重心，不写进标题）

### 应用服务型

有明确运行进程的后端服务、后台、定时任务、消息消费等。

主轴：仓库定位 → 功能模块清单 → 核心业务流程。

### 多模块 / 聚合工程型

多子项目、多子服务共仓。

主轴：子模块职责地图 → 模块依赖方向 → 可独立运行模块与共享模块的区分。

### 暂未定型 / 证据不足

不要强行包装成完整业务系统。优先写：当前直接拥有的能力、可证实的模块边界与流程、待确认的上下游。

## 整体结构：先业务，后技术

- **业务篇**：回答解决什么问题、业务职责、核心主线。不出现启动命令、配置项、接口地址等操作细节。
- **技术/工程篇**：稳定模块边界、核心流程、少量架构阅读入口，把业务心智映射到代码心智。

默认六节顺序（明显不适配时才可跳过）：

1. 标题与一句话定位  
2. 快速总览  
3. 业务背景与主线  
4. 全局架构与接手入口  
5. 功能模块清单  
6. 核心业务流程  

## 第一原则（业务）

- 前半答业务问题与职责，后半答模块与流程；**不展开**启动命令、配置 key、调试入口
- 是**项目级顶层视野 + 简洁接手框架**，不是代码说明书或详细设计
- 默认只写功能层与模块边界；仅在「全局架构与接手入口」中点到少量目录/入口文件/入口类
- 接手入口只答「改什么先看哪里、为什么、别先看哪里」；控制在 `3–6` 个锚点
- 入口必须是长期稳定架构锚点（主服务入口、路由聚合、领域编排、模块门面）；不要列 DTO、临时脚本、底层工具类
- 功能模块清单和核心流程是主叙事，不要后置到附录
- 启动命令、环境变量、接口地址、Topic 清单、包结构图等操作细节**不纳入**根目录 README

## 输出结构

### 1. 标题与一句话定位

完全面向业务，不讲技术栈（可选极短技术栈短语，不能盖过定位）。

必须包含：

- 项目名称
- 1 句：解决什么业务问题
- 1 句：在系统中承担什么业务职责
- 1 句：直接拥有的能力 vs 不直接拥有的外部能力

推荐写法：

> `xxx` 主要负责 `{本仓库直接拥有的能力}`。它接住 `{输入/触发}`，完成 `{核心处理}`，再把 `{结果}` 交给 `{下游系统/用户}`。

> 如果只用一句话理解：`xxx` 是 `{业务对象}` 从 `{进入系统}` 到 `{被处理/被输出}` 的主干工程。

### 2. 快速总览

一屏内让读者知道系统是做什么的。

建议：

- **2–4 行**开场摘要（自然语言端到端主链路，避免模板填空）
- **1 张极简主链路图**（可选）：3–5 个业务阶段节点
- **1 张项目事实表**（可选；文字已够清楚则不加）

事实表推荐列：系统形态 | 核心主线 | 主要场景 | 主要对象。  
不出现技术细节列。写不出具体信息的行就删掉。

### 3. 业务背景与主线

回答「为什么要有这个系统」和业务大图中的角色。

必须包含：

- 系统承担的业务职责（分点）
- 业务定位判断（按当前结构更像什么形态）
- 核心业务主线表：

| 阶段 | 主角模块 | 核心动作 |
|------|----------|----------|

阶段名用业务语言；只列主线，不列异常/校验/转换分支。

### 4. 全局架构与接手入口

给长期有效的架构锚点，帮助把项目模型映射到目录/模块/入口。

默认在这些情况下保留：新人接手、多模块难找入口、业务信息够但缺第一跳、需要当简洁目录用。

推荐表：

| 改什么 / 看什么 | 先看哪里 | 为什么是入口 | 暂时别先看 |
|-----------------|----------|--------------|------------|

写法：

- 优先目录、子模块、模块 README、启动模块、主链路入口；必要时才点稳定入口类
- `3–6` 个锚点，不做穷举
- 不出现方法名、SQL、字段名、配置 key
- **不写**启动命令、联调步骤、环境依赖、排障手册

### 5. 功能模块清单

不是目录树或包清单，而是「有哪些功能模块、各做什么」。

| 模块 | 一句话职责 | 不做什么（容易混淆的边界） |
|------|------------|---------------------------|

- 一句话职责写完整句，尽量控制在 20 字内
- 「不做什么」只写最易混淆的边界；无则留空
- 通用支撑不要抬成主模块
- **禁止**包名/类名/接手入口列；**禁止**「上游输入/下游输出/对接方式」类碎片宽表
- 可选极简层次图：只用功能职责名

### 6. 核心业务流程

一张极简流程图即可，不另配阶段表。

- 默认 3–5 节点，硬上限 7
- 节点用业务阶段名；可附带负责模块名，但不要变成模块清单
- 只画主干；不展开模块调用与对象变更细节
- 图外补充最多 1–2 句

## 更新已有 README（业务）

- 保留有价值内容；优先前置项目总览
- 可新增「全局架构与接手入口」，不要把开发手册整段搬进 README
- 旧的启动方式、接口清单、包结构图等操作性细节建议迁出根 README
- 不为统一风格而全文重写

## 图表与语言

### 图

- 默认 1–2 张：结构图（可选）+ 核心流程图
- 单图优先 ≤7 节点，硬上限 10；节点用功能名，不用 Controller/Service/DAO

### 表

- 一张表一个问题；默认 4–6 行；接手入口表 ≤4 列
- 超过 4 列先考虑拆表

### 表达

- 先结论后展开；段落短、句子直
- 业务篇首句先写职责/痛点/主线，不先写愿景或技术栈清单
- 用功能视角词汇；仅在接手入口节少量点名目录/入口类
- 推断用「按当前结构看更像…」；内外能力分开写
- 接手入口解释阅读顺序，不是操作步骤

### 去 AI 味

- 不用模板套话开头
- 不为完整而连续堆图表/澄清
- 不默认「常见误解」大全；不写研究过程
- 少用加粗；少堆「全/完整/统一/闭环」等抽象词

## 常见反模式（业务）

- 写成业务介绍却说不清模块；或只剩目录列表
- 业务篇一上来愿景/术语/技术栈大段
- 接手入口膨胀成开发手册（启动、联调、排障）
- 项目知识图谱味 / 项目记忆味 / 全套 AI 模板铺满
- 模块只列 controller/service/dao；流程只有抽象阶段名
- 写入启动命令、配置 key、环境变量、Topic 清单
- 把命名或外部协议上升成自有核心能力；脑补未证实的业务闭环
- 过宽对接表把关系拆成碎片

## 输出前检查清单（业务）

- [ ] 1 分钟内知道项目做什么
- [ ] 业务篇讲清职责、痛点、核心主线
- [ ] 需要时给出 3–6 个接手锚点，且未膨胀成手册
- [ ] 功能模块清单靠前；有明确核心流程与先后顺序
- [ ] 无包结构/对象流转/生命周期详细设计
- [ ] 无启动命令、接口地址、配置 key、包结构图抢主轴
- [ ] 模块分工体现「负责什么 / 易混边界」
- [ ] 未粗暴删除原文有效内容
- [ ] 证据不足处已保守改写或省略
- [ ] 无 AI 模板味、无项目记忆味
