# 业务项目 README 规范

适用：后台/中台、业务服务、有业务主线的应用、多模块业务聚合工程。  
读者：开发接手。目标：**3 分钟建立心智模型，10 分钟知道从哪里接手。**

返回 [`SKILL.md`](../SKILL.md) 完成读者判定后阅读本文。

## 业务子类型（只影响重心，不写进标题）

### 应用服务型

有明确运行进程的后端服务、后台、定时任务、消息消费等。

重心：定位 → 主链路 → 模块。读者常需要把服务跑起来联调时，补一块精简运行信息（见下文「运行与配置」块）。

### 多模块 / 聚合工程型

多子项目、多子服务共仓。

重心：子模块职责地图、模块依赖方向、可独立运行模块与共享模块的区分。

### 暂未定型 / 证据不足

不要强行包装成完整业务系统。优先写：当前直接拥有的能力、可证实的模块边界与流程、待确认的上下游。

## 内容块菜单（不是固定骨架）

先列读者最可能问的 2–4 个问题，从下面挑块回答。**块可省、可并、可重排；章节名从项目内容长出来**——写「一条消息怎么走到用户手里」，不写「快速总览」「核心业务流程」这类通用名。

### 块：一句话定位（必写）

1–2 句直接断言：这个仓库干什么、边界在哪。要求：

- 用项目自己的词汇；**禁止套用任何固定句式**（反面教材见 [`examples.md`](examples.md) 反例 1）
- 边界要说具体的：什么能力在别的仓库/系统做，点名
- 可选极短技术栈短语，不能盖过定位

### 块：主链路（推荐）

- 一段话或一张 3–5 节点图说清端到端主干
- **全篇只出现一次**；其它块需要引用主链路时，用文字回指，不重复画图

### 块：业务背景与主线（可选）

- 回答「为什么要有这个系统」；分点列承担的业务职责
- 主线写业务阶段，只列主干，不列异常/校验/转换分支
- **不写"定位判断"**：定位结论融进开场陈述（"统一入口"本身已说明它是接入层），不单独成句

### 块：上下游与外部边界（集成层/中台/读者关心协作时必写）

- 谁调我、我调谁、同链路但不经过我的邻居
- 写真实项目名、真实机制（入口类、字段路径、协议）、真实防混淆提醒（"改我不等于改 X"）
- 对集成类仓库这往往是最有价值的一块，可以放很靠前；用户点名要时尤其如此

### 块：功能模块清单（推荐）

- 模块 + 一句话职责（完整句，尽量 20 字内）；最易混淆的边界一句话带过
- 表格或分点都行；填不出真边界就不写那列，不凑单元格
- 通用支撑不抬成主模块；不列包名/类名/「上下游输入输出」碎片宽表

### 块：接手锚点（多模块、入口难找时要）

- 3–6 个长期稳定锚点：改什么先看哪里、为什么是入口
- 优先目录/子模块/启动模块/主链路入口，必要时才点稳定入口类
- 不列 DTO、临时脚本、底层工具类；不膨胀成开发手册（不写启动命令、联调步骤、排障）

### 块：运行与配置（混合形态：读者需要跑起来时保留）

- 首选启动命令、关键环境变量、端口/健康检查，精简、可复制
- 详细运维、排障另放 docs；从旧 README 收编时保留核心，不整段照搬

## 表达规则

- 直接断言。本规范**不提供句式模板**，也不要模仿任何"推荐写法"的句式
- **禁元叙述**：不写「按当前结构看更像…」「如果只用一句话理解…」「本 README 将…」这类谈论文档本身的句子
- 每个论断尽量带真实锚点（项目名/模块名/数字/机制）；写不出锚点的段落多半可删
- 表格全篇默认 ≤2 张；一张表只解决一个问题；列填不出真内容就删列
- 图 0–2 张；节点用功能/业务名，不用 Controller/Service/DAO；单图 ≤7 节点
- 段落短、句子直；先结论后展开
- 少用加粗——只给真正的边界警示用；少堆「全/完整/统一/闭环」等抽象词
- 推断用「更像…」一次带过，不专门成句；内外能力分开写

## 更新已有 README（业务）

- 保留有价值内容；**可操作内容（命令、配置、端口、示例）只能保留或迁移，不得删除**，迁移留指针
- 可新增接手锚点，不要把开发手册整段搬进 README
- 旧的启动方式、接口清单、包结构图等可精简或迁出根 README，但读者需要跑起来时必须保留核心一块
- 不为统一风格全文重写；只动需要动的部分
- 用户点名要的内容优先满足、放前面，不被其它章节稀释

## 常见反模式（业务）

- 开头两句像句式填空（「它接住…完成…再把…交给…」「如果只用一句话理解…」）
- 元叙述定位句（「按当前结构看，更像…而不是…」）
- 同一主链路在不同章节反复画图/列表
- 表格出现填充物单元格（为凑列而写，如把「当前不依赖真实库」塞进「不做什么」列）
- 凑结构的一行事实表，信息正文已有
- 重构后原文的启动/配置内容凭空消失
- 写成业务介绍却说不清模块；或只剩目录列表
- 业务篇一上来愿景/术语/技术栈大段
- 接手锚点膨胀成开发手册（启动、联调、排障）
- 项目知识图谱味 / 项目记忆味 / 全套模板铺满
- 模块只列 controller/service/dao；流程只有抽象阶段名
- 把命名或外部协议上升成自有核心能力；脑补未证实的业务闭环
- 过宽对接表把关系拆成碎片

## 输出前：阅读测试

- [ ] 换名测试：遮掉项目名这段话还成立吗？成立 → 改具体或删
- [ ] 抽删测试：删掉某节/表/图，读者会察觉吗？不会 → 删
- [ ] 首屏测试：1 分钟内知道项目做什么、边界在哪吗？
- [ ] 保留测试：原文的可操作内容还在吗（或迁移留了指针）？
- [ ] 重复测试：主链路/流程/关系只出现一次吗？
- [ ] 锚点测试：每个论断有具体锚点吗？接手锚点 3–6 个且未膨胀成手册吗？

收尾自问：更像「总览 + 接手框架」，还是业务介绍/详细设计/知识图谱/分析报告？第一次接触的人能否立刻知道职责、模块和流程？
