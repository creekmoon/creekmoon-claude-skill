# README 正反样例对照

素材来自一次真实重构：对 `12times-n8n-facade`（Spring Boot 能力入口服务，n8n 编排回打雀雕能力的 HTTP 入口）执行「重构 README，专门梳理上下游项目关系」。

**用法**：写正文前快速过一遍，对照检查自己有没有写出同款模板话。正例示范的是"具体 + 直接"的写法，**不要照抄它的句式**——照抄正例和照抄模板是同一种病。

## 反例 1：模板填空式开场

❌ 实际产出：

> `12times-n8n-facade` 主要负责 **n8n 编排侧回打雀雕能力的唯一 HTTP 入口**。它接住 n8n 节点发出的能力调用，完成鉴权、打点与分发（mock 内嵌应答 / real 透传），再把同路径请求交给下游 ChatBot 业务聚合层。
>
> 如果只用一句话理解：本仓库是「n8n 工作流 ↔ 雀雕 ChatBot 能力」之间的编排接入层……

问题：

- 「它接住…完成…再把…交给…」是填空句式，换任何项目都成立 → 换名测试必挂
- 「如果只用一句话理解」是元叙述：在谈论这份文档，而不是讲这个项目
- 加粗堆叠，读起来像广告

✅ 改写（直接陈述，边界点名到具体仓库）：

> n8n 工作流回打雀雕能力的统一 HTTP 入口。nodes 的 16 个 capability 调用都打进这里：mock 模式内嵌应答，供 nodes 联调断言；real 模式原样透传到 damselfish-chat-bot 的同路径接口。IM 发送、CRM、企微等业务实现都在 ChatBot，本仓库不做。

## 反例 2：凑结构的一行事实表

❌ 实际产出：

> | 系统形态 | 核心主线 | 主要场景 | 主要对象 |
> |----------|----------|----------|----------|
> | 编排接入层（Spring Boot 应用） | n8n 能力回打收口 | nodes 联调（mock）/ 生产透传（real） | 16 个 capability 端点 |

问题：四列抽象列头，信息全是正文已有内容的压缩；唯一的新信息（16 个端点）被压成了名词。

✅ 做法：整张删掉。「16 个端点」这种真信息并进开场句子（见反例 1 的改写）。

## 反例 3：元叙述定位句

❌ 实际产出：

> 按当前结构看，更像**集成适配层上的应用服务**，而不是业务域中心。

问题：这是分析报告的结论句——读者不需要知道写作者的心路历程；「按当前结构看」是在给自己的论断留退路。

✅ 做法：删掉。定位结论融进开场陈述——「统一 HTTP 入口」本身已经说明它是接入层。

## 反例 4：同一主链画三遍

❌ 实际产出：同一条「ChatBot 触发 → n8n 编排 → facade 回打 → ChatBot 落地」主链，先后出现在：

1. 「快速总览」的 ASCII 图
2. 「上下游项目关系」的 ASCII 图
3. 「核心业务流程」的 mermaid 图

问题：每个章节都被要求"有自己的图"，读者被迫把同一内容读三遍；三份图略有出入时还增加校对负担。

✅ 做法：主链路全篇只画一次，放在读者最需要它的章节（这个仓库里就是「上下游」章）；其它章节用文字回指（"主链路见上游图"）。

## 反例 5：为填满列硬凑的表格单元格

❌ 实际产出（模块清单表的一行）：

> | MPG 子模块 | 按需生成符合规范的 CRUD 脚手架 | 当前主路径不依赖真实库 |

问题：「不做什么」列的第三格不是边界，是现状描述——因为规范要求这列存在，只能硬凑。读者被误导去寻找一个不存在的"边界"。

✅ 做法：填不出真边界，那一格留空或直接删列；多数模块写不出"不做什么"时，说明这列本来就不该存在。

## 反例 6：重构把"怎么跑"删没了

❌ 实际发生：旧版 README 有构建命令、本地启动、环境变量（`FACADE_MODE` / `NACOS_ENABLED`）、MOCK/REAL 模式切换、端口与健康检查、MPG 模块用法——因为这个仓库被判成"业务项目"，这些内容按"启动命令不纳入根 README"的规则被整段删除。而这个服务恰恰是对内联调设施：nodes e2e 预设它已启动，联调方第一眼就需要这些。

✅ 做法：可操作内容只能保留或迁移，不得删除。读者需要跑起来的服务类仓库，保留一块精简的「运行与配置」：首选启动命令、关键环境变量、端口/健康检查，详细运维迁到 docs 并留指针。

## 正例：为什么"上下游关系"一章反而最像人写的

同一份 README 里，用户点名要的「上下游项目关系」章质量明显高出其它章节。摘录：

> 不要把它当成 ChatBot 或 n8n 本身。

> nodes e2e **预设本服务已启动**，并读 mock 调用记录做断言。

> `OrchestratorRouter` 在闸门后异步 POST n8n Webhook，并把 `_context.callbackUrl` 指到 facade 的 `sendImMessage`；**并不 HTTP 调用 facade 来「启动编排」**。

> 批量与运营任务主链本期未接入 n8n 回打收口；不要默认「改 facade = 改群发/SOP」。

好在哪：

- **具体**：真实项目名、入口类名、字段路径，每个论断都能落到代码
- **有立场**：「刻意不接」「并不调用」——敢下判断，不用中性废话和稀泥
- **防混淆**：主动纠正读者最可能的误解（"改 facade = 改 SOP"）

这一章好不是偶然：它是用户点名要的，写作时直奔真实问题，没有走骨架。**用户点名的内容往往就是读者最关心的——放前面、写足。**
