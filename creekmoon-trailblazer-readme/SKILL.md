# 项目 README 分场景写作技能

这个技能只做一件事：**按仓库类型写对根目录 README**——业务项目让人快速建立全貌并知道从哪里接手；工具类项目让人尽快用起来。

写之前必须先判定场景，再读对应 reference，不要用同一套章节硬套所有仓库。

如果仓库已经有 `README.md`，默认做 **增强式重构**，保留有价值内容，不直接推倒重写。

## 适用场景

- 用户要新建、重构、补强或精简根目录 README
- 业务侧：项目总览、功能模块、核心流程、模块边界、新人接手入口
- 工具侧：安装、启动、配置、调用示例、能力边界（能做什么 / 不能做什么）
- 用户说 README 看完仍不知道项目做什么，或不知道怎么跑起来
- 用户觉得 README AI 味重、像模板或知识图谱，需要压成高价值引导

## 不适用场景

- 只写接口字段与请求/响应示例的完整 API 文档（用专门的 API 文档技能）
- 只写运维部署手册、排障大全、环境变量百科（可作工具 README 的一小段，但不能单独膨胀成运维书）
- 单个模块的详细设计、类图、对象生命周期、项目知识图谱 / 项目记忆
- 需要跨仓库做完整业务归因的深度研究报告
- 逐行解释代码实现细节

这些内容可以存在于仓库其它文档，但不应该抢走根 README 的主轴。

## 第一步：判定场景（第一闸门）

动手写正文前，先判成下面两类之一。类型只影响叙事主轴，不要在 README 里贴「业务项目 / 工具类」标签。

### 工具类项目

读者第一问是：**怎么装、怎么启、怎么调？**

典型形态：CLI、MCP Server、SDK、中间件插件、脚手架、可独立安装运行的能力组件、开箱即用的服务式工具。

判定线索（命中越多越偏向工具）：

- 有明确的安装/镜像/包发布路径（Docker、npm、pip、二进制等）
- 对外暴露 tools / commands / 少量 API，使用者按「调用面」理解
- 现有文档或用户诉求强调「快速启动 / 接到客户端 / 环境变量」
- 没有（或不需要）长业务主线与多角色业务闭环

→ 判定为工具后，**立即 Read** [`references/tool.md`](references/tool.md)，按其中章节顺序写。

### 业务项目

读者第一问是：**业务是什么、模块怎么分、改哪先看哪？**

典型形态：后台/中台、业务服务、有业务主线的应用、多模块业务聚合工程。

判定线索（命中越多越偏向业务）：

- 有端到端业务对象与阶段（下单、审批、结算等）
- 接手成本主要在「理解职责与模块边界」，而不是「跑通一条安装命令」
- 用户明确提到新人接手、仓库导览、模块协作、核心流程

→ 判定为业务后，**立即 Read** [`references/business.md`](references/business.md)，按其中章节顺序写。

### 模糊时

1. 先补问 1 个问题：这份 README 更希望读者「马上用起来」，还是「理解业务并接手改代码」？
2. 用户暂时无法补充时：有清晰「安装 / 启动 / 配置 / 调用」主路径 → **工具**；否则 → **业务**。
3. 既像业务系统又像集成适配层时，优先写「本仓库直接拥有的能力」，不替其它系统补全业务闭环。

## 共享原则（两边都遵守）

- **结论强度不超过证据强度**：先写代码和现有文档已证明的，再写保守判断
- 目录名、类名、DTO 字段、注释、行业术语只能作线索，不能单独证明定位或完整业务域
- 图和表都要短；一张表只解决一个问题；不为了完整硬堆图表
- 不把 README 写成一次性 AI 分析报告或审计报告；保留长期有效的结构判断
- 判断不清时用中性表述；必要时只补 1–2 行待确认，不强定性
- **增强式重构**：保留原文有价值内容，只在重复、冲突、失效时删改

### 场景条件化（关键）

| 规则 | 业务项目 | 工具类项目 |
|------|----------|------------|
| 启动命令、环境变量、接入配置 | **不作为主轴**；默认不写入根 README | **就是主轴**；首选路径要可复制可跑 |
| 架构 / 模块 / 接手入口 | 技术篇核心：模块边界 + 3–6 个接手锚点 | **点到为止**（可选短节）；不得压过用法 |
| 业务主线 / 阶段表 | 主叙事 | 通常不写；改写「能做什么 / 不能做什么」 |
| 详细设计、包结构、对象流转 | 不写 | 不写 |

## 信息收集（先判场景，再按表收集）

两边都先看：现有 `README.md`、根构建文件、顶层目录、Docker / CI。然后分岔：

**业务项目**（详见 `business.md`）：

| 优先级 | 目标 | 读什么 |
|--------|------|--------|
| 1 | 定位与类型 | README、构建文件、顶层目录 |
| 2 | 功能模块 | 子模块、模块 README、核心功能入口 |
| 3 | 接手锚点 | 启动模块、主链路入口、少量稳定入口类 |
| 4 | 核心业务流程 | 最短可解释的端到端路径 |
| 5 | 外部边界 | 依赖的外部系统、协议、存储 |

**工具类项目**（详见 `tool.md`）：

| 优先级 | 目标 | 读什么 |
|--------|------|--------|
| 1 | 能力与边界 | README、对外 tools/commands/API、安全/只读声明 |
| 2 | 首选启动路径 | Docker/compose、发布镜像、一键安装脚本 |
| 3 | 配置与接入 | 环境变量、客户端配置示例、端口/健康检查 |
| 4 | 最小可跑示例 | 官方示例、inspector、调用顺序 |
| 5 | 架构点到为止 | 入口文件、顶层目录（仅二次开发需要时） |

命名只作辅助线索。在能说清该场景主轴之前，不要开始写正文。

## 写正文前的轻量审查

落笔前整理候选结论（可只在思考中完成，不必输出给用户）：

| 候选结论 | 证据类型 | 当前判断 | README 写法 |
|---------|----------|----------|-------------|
| 场景（业务 / 工具） | 直接证据 / 弱线索 | 可直接写 / 需保守 | 按对应 reference |
| 项目定位 / 一句话能力 | 同上 | 同上 | 主结论或保守表述 |
| 主路径（业务主线 或 启动/调用路径） | 同上 | 同上 | 主轴章节 |
| 边界（不做什么 / 外部能力） | 同上 | 同上 | 必须写清易混边界 |

- **直接证据**：现有 README、主流程、运行配置、对外工具表、模块协作
- **弱线索**：目录名、包名、类名、注释、单个 adapter
- 激进与保守解释并存时，选保守；证据不足且不影响主线则宁可不写

## 输出前短检（分流）

**业务：** 1 分钟内知道做什么；有模块边界与核心流程；接手锚点未膨胀成手册；无启动/配置主轴抢戏。  
**工具：** 按首选路径能跑起来；写清能做/不能做；配置与调用示例可复制；架构未压过用法；首选与备选路径主次分明。

两边共用：未粗暴删掉原文有效内容；无 AI 模板堆砌；无把命名上升成已证实事实。

细则与完整检查清单见对应 reference。

## 建议输出风格

- 默认输出根目录 `README.md`
- 标题简短，章节层级不超过两层
- 图简洁、表精简
- **先判定场景 → Read 对应 reference → 再写正文**

## 示例触发语句

**业务：**

- 「帮我重写项目 README，让新同学快速了解项目是做什么的。」
- 「README 看完还不知道有哪些模块，改成项目总览。」
- 「补接手入口：改某类能力先从哪里看。」

**工具：**

- 「按开箱即用重写这个 MCP/CLI 的 README。」
- 「README 重点写怎么 Docker 启动、怎么接到 Cursor、有哪些工具。」
- 「用法说明太散，收成一份能直接跑起来的根 README。」
