# 页面结构决策

结构是本技能的核心职责：轨道、页面形态、布局骨架、信息分区、可用性硬规则，最终落成 ASCII 骨架图和灰阶线框。这一层决定产出"对不对"；视觉质感（配色、字体、阴影、动效）决定"好不好看"，属于下游增强层（如 creekmoon-aglaea-design），本文件不涉及。

先定轨道，再定页面形态，然后选布局骨架，最后排信息分区。跳过前几步直接罗列组件，是布局呆板、表达失焦的根源。

## 第一步：判断轨道

| 轨道 | 覆盖 | 优化目标 |
|------|------|---------|
| **产品界面** | 后台、看板、管理台、设置页、内部工具、开发者工具 | 信息密度、安静的 chrome、可扫视性、工具文案 |
| **营销页面** | 落地页、官网、定价页、作品集、推广页 | 视觉冲击、叙事、单一转化路径 |

一句话检验：**说服陌生人 = 营销；让操作者干活 = 产品。** SaaS 的官网是营销轨道，登录后的应用是产品轨道，两者分开设计，不共用一套信息密度。

判错轨道是表达错误，不是审美问题——把营销轨道套在产品界面上，就会出现"看板顶上放 hero 区、卡片里写口号"的灾难。轨道结论要显式写进产出，供下游（设计、开发）直接消费。

## 第二步：判断页面形态

页面形态由用户任务决定，不由内容数量决定。先回答：用户来这个页面，是要**感知全局**、**找到对象并操作**、**理解单个对象**、**提交信息**，还是**按步骤推进**？

| 形态 | 用户任务 | 结构要点 |
|------|---------|---------|
| 看板 Dashboard | 感知状态、发现异常、看趋势 | 指标要有主次和关联（状态→原因→影响→入口），不是等大卡片阵列；异常要能点进去 |
| 管理台 Console | 筛选、批量处理、进详情 | 筛选区紧贴结果区；表格是主角，占最大面积；批量操作在选中后出现 |
| 详情页 Detail | 理解单个对象、执行动作 | 顶部对象摘要（名称、状态、主操作），下方分区展示属性/历史/关联 |
| 表单页 Form | 提交一件事 | 单列布局，相关字段分组，主按钮在末尾左对齐或吸底；不要双列表单 |
| 工作流 Workflow | 按步骤推进 | 当前步骤、已完成、未完成清晰；说明卡住的前置条件；支持回退 |
| 落地页 Landing | 被说服、转化 | 一条主转化路径、一个重复出现的 CTA、证据（案例/数据/口碑）就近支撑主张 |

页面同时承担多种任务时（混合形态），明确哪个任务是主线，其余内容降级为侧栏、抽屉、标签页或二级页面，不要平铺。

## 第三步：选布局骨架

| 骨架 | 适用 |
|------|------|
| 侧边栏 + 内容区 | 多模块后台的默认选择；内容区是主角，侧栏要安静 |
| 顶部导航 + 内容区 | 模块少（≤5）或内容需要全宽 |
| 列表-详情分栏 | 邮件式：左列表右详情；移动端退化为两级页面 |
| 上下分层 | 先全局摘要再明细：顶部一行关键数字，大面积留给明细表 |
| 居中单列 | 表单、登录、设置、文章 |

具体实现尺寸（侧栏宽度、导航高度、内容区最大宽度等）属于实现细节，由下游把选定骨架落地时决定。

营销页面的分区排布：hero（一句话主张 + 主 CTA）→ 产品实证（截图/演示）→ 特性分组 → 社会证明 → 定价 → 尾部 CTA。每个区块只讲一件事，删掉重复表达同一情绪的区块。

## 第四步：信息分区

把页面内容归入四类，按优先级排位：

- **核心决策区**：用户必须先看的状态、结论、关键数据、风险——放首屏最高视觉权重的位置。
- **辅助信息区**：解释、历史、明细、参考——可折叠、可下钻、可放次要位置。
- **操作区**：主操作与判断依据相邻；危险操作与普通操作物理分离；每屏只有一个主按钮。
- **反馈状态区**：加载、空数据、错误、成功的呈现位置，结构阶段就要预留。

排序原则：

- 首屏只放做出下一步判断所需的信息。能下钻的不并列，能折叠的不抢首屏，能筛选得到的不重复展示。
- 解释性内容紧贴被解释对象，不要集中堆到页面底部。
- 指标之间要有关系（因果、对比、递进、阈值），没有关系的并列数字应该删除、合并或降级进表格。

## 可用性硬规则

以下规则缺了会"错"，不是"不好看"，因此属于结构层职责。产出骨架和线框时逐条核对：

- **每屏一个主操作**：主按钮唯一，其余动作降级为次级或文本操作。
- **危险操作与普通操作物理分离**，且需要二次确认或可撤销；确认按钮写明动作和对象（"删除 3 个项目"，不是"确定"）。
- **状态完整**：每个屏幕的 loading / empty / error / partial success 都要进状态清单；"没有数据"和"取不到数据"是两种不同的信息，不许合并。
- **错误信息具体且可行动**：写清发生了什么 + 用户能做什么，恢复动作出现在失败现场，不藏在别处。
- **表单单列**，相关字段分组；只有强关联短字段（省/市、起止日期）才共行；label 必须可见，不用 placeholder 承载说明。
- **触控目标 ≥ 44px**，移动端主操作在拇指可达区。
- **工作界面用工具文案**：说明位置、状态、动作，不写营销口号；营销语言只属于营销轨道。
- **可访问性基线**：语义化结构、键盘可达、表单控件有 label——这些是需求，不是样式。

## 产出格式：ASCII 骨架图

每个屏幕产出一张低保真骨架，确认"用户先看什么、再做什么"成立，并标注信息分区。例如管理台：

```text
┌──────────┬──────────────────────────────────────┐
│ 侧栏      │ 页面标题                    [主操作]  │ ← 操作区
│ (安静)    ├──────────────────────────────────────┤
│          │ [筛选] [筛选] [搜索____]     共 128 条 │
│          ├──────────────────────────────────────┤
│          │ 表格（主角，占最大面积）                │ ← 核心决策区
│          │  名称    状态    数量↗   更新时间  操作 │
│          │  ...                                  │
│          ├──────────────────────────────────────┤
│          │ 分页                                   │ ← 辅助信息区
└──────────┴──────────────────────────────────────┘
（loading/empty/error 状态复用表格区域 → 反馈状态区）
```

骨架确认后，结构即冻结进灰阶线框（见 prototype-guide.md）；下游设计只加质感，不改结构。
