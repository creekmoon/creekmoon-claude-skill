# 场景 A：画布布局与节点命名

布局是工作流的"第一印象"。一张整洁的画布让维护者 10 秒看懂主线；一张乱画布让人连数据从哪来到哪去都理不清。命名是布局的另一半——节点名就是画布上的路标。

## A1. 布局规则

### 方向与对齐

- **主流水线从左到右**：触发器固定在 `x ≈ 0` 的最左列，处理节点按执行顺序向右递增。
- **同层节点 y 对齐**：同一逻辑阶段的节点放在同一水平带（y 坐标相同或相差 < 40）。
- **错误/兜底分支统一向下**：成功主线保持水平，错误分支、兜底分支放在主线上方或下方至少 110px 处，与成功线视觉分离。
- **坐标取 20 的倍数**：n8n 画布有吸附网格，所有 position 对齐到 20 的倍数，避免节点"差几个像素"的邋遢感。

### 间距

- 相邻节点 **x 间距 ≥ 220px**（节点本身约 120px 宽，220 保证连线舒展）
- 同列/相邻层 **y 间距 ≥ 110px**
- **禁止节点重叠**：两个节点 x 间距 < 220 且 y 间距 < 110 即判定过近（有连接关系的连续节点除外，但 x 间距仍须 ≥ 220）

### 分支走向约定

- IF / Switch 的分支走向全画布统一：建议 **true 直行/向上，false 向下**；团队另有约定的从团队约定，但一张画布内必须一致。
- **避免连线交叉**：出现交叉连线说明分层出了问题——优先重排节点消除交叉，而不是拉一条斜线过去。
- 循环（Loop Over Items 回到上游）允许回边，但回边尽量走画布上方或下方的"环路走廊"，不横穿主线。

### 分区与注释

- **节点数 > 10** 时用 Sticky Note 或 `nodeGroups` 分区：每个功能区一块（如「数据拉取」「清洗转换」「通知发送」），写明该区职责。
- **禁用节点要么删、要么停进停车场**：暂时不用但想保留的，移到画布底部（y 明显大于主线，如主线 y=300 则停车场 y≥800），加 Sticky Note 说明为什么留着。禁止 disabled 节点散落在主线中间干扰阅读。

### 布局检查清单（可程序化执行）

- [ ] 触发器在最左列（x 最小）
- [ ] 所有 position 为 20 的倍数
- [ ] 无节点重叠/过近（规则见上）
- [ ] 主线节点 y 对齐（同一水平带）
- [ ] 错误分支向下且与主线分离
- [ ] 无连线交叉
- [ ] 大画布已用 Sticky Note / nodeGroups 分区
- [ ] disabled 节点集中在停车场区域

## A2. 命名规则

### 节点名 = 动词 + 业务对象

读者扫一眼节点名，就该知道这个节点**对什么业务数据做了什么**。

**中文优先，术语保留英文**：节点名用中文（团队母语扫读成本最低）；专业名词、技术术语没有通行中文译法的可保留英文（如 Webhook、HTTP、ID、token、API 名）。禁止整节点名用英文造句——`tool_search_memory` 式命名把中国团队拖回二速阅读。

- 正面：`查询待发货订单`、`组装通知消息内容`、`按ID查询客户档案`、`校验库存是否充足`
- 反面（默认名）：`HTTP Request 1`、`Set 2`、`IF 3`、`Code 1`
- 反面（英文造句）：`tool_search_memory`、`fetch_history`、`reply_message`——非术语的英文命名
- 反面（纯技术描述）：`转换`、`处理`、`判断`——没说清处理的是什么业务对象
- 反面（长句）：`然后我们需要把查询到的订单数据做一个格式上的转换以便后续使用`——节点名不是注释，控制在 15 字内

### 同类型多节点的区分

同类节点出现多次时，用限定词区分，禁止 `xxx 1 / xxx 2`：

- 正面：`查询订单-按ID`、`查询订单-按时间窗`
- 正面：`发送通知-即时消息`、`发送通知-邮件`

### 工作流命名

`[业务域] – 描述`，如 `[订单] – 发货超时告警`、`[客服] – 会话摘要每日推送`。同名工作流并存时（测试/生产各一份）加环境后缀。

**已有工作流的改名只在用户明确要求时执行**——名字是身份标识，被文档、监控和同事习惯引用；检查中觉得不规范，写进报告建议区，不得顺手改掉。

### 重命名的连锁同步（易漏！）

节点名是 connections 的 key，也是表达式的锚点。**n8n 重命名只自动更新 connections，不会更新表达式和 prompt 文本**——所以重命名节点 `旧名 → 新名` 必须手动同步：

1. `connections` 对象里以 `旧名` 为 key 的条目（以及它作为 target 出现的 `node` 字段值）——n8n 自动处理
2. 全工作流参数中的 `$node["旧名"]`、`$('旧名')`、`$node.旧名` 表达式——**n8n 不自动处理，必须人工全量搜索替换**
3. 执行历史里的旧名只是记录，不用管；但 pinData 若挂在旧名节点上要一并迁移
4. **Agent 工具节点**：工具名由节点名派生，system prompt 和兄弟工具描述里按名引用它的地方必须同步改（如 prompt 里写"调 tool_search_memory"，节点改名后引用名要跟着改，否则模型按旧名找不到工具）

改完后全量拉取工作流搜索旧名确认零残留，再用 `validate_workflow` 过一遍。

### 命名检查清单

- [ ] 无 `HTTP Request N` / `Set N` / `IF N` / `Code N` 式默认名
- [ ] 每个节点名都含"动词 + 业务对象"
- [ ] 同类节点有限定词区分
- [ ] 无超过 15 字的长句名
- [ ] 工作流名符合 `[业务域] – 描述`
