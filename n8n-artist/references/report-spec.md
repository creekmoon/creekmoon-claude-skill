# 检查报告规范（统一格式）

所有检查/体检/评分任务只输出这一种报告。设计目标：编排使用者 30 秒内决定"修不修、先修哪"；**篇幅与问题数成正比，与节点数脱钩**——100 个节点的健康工作流也只有半页，3 个问题的报告就写 3 行。

## 六区结构（自上而下）

### 1. 结论区（决策）

一行定生死：

- 评分任务：`总分 XX/40（定级）—— 一句话结论。必须修复 N 项，提示 N 条。`
- 检查任务（不打分）：`结论：🟢/🟡/🔴 —— 一句话结论。`

### 2. 必须修复区（阻断性问题）

只放阻断性问题：失效引用、表达式语法错误、运行中反复失败、工具调用链断裂。没有问题就写"无"。

| # | 节点 → 位置 | 问题 | 修法 |
|---|------------|------|------|

### 3. 得分区（维度定位）

评分任务才有。每个维度一行，只写最主要的失分点：

| 维度 | 得分 | 主要失分点 |
|------|------|-----------|
| 命名 | 9/10 | 2 个默认名 |
| 历史运行 | N/A | 无执行数据，总分按 30 分制 |

### 4. 节点区（精确定位）

| 节点 | 结果 | 命中项 |
|------|------|--------|
| HTTP Request 3 | ✗ | 默认名 |
| 组装通知 | △ | `$json.orderNo` 字段级失效待验证 |

结果标记：`✗` 有扣分/问题，`△` 有待验证项，`✓` 通过。

**通过节点不逐个罗列**：连续通过的合并为一行「其余 N 个节点 ✓ 通过」。节点区只呈现有情况的节点。

### 5. 提示区（不扣分的建议）

只列不纳入评分的建议（如外部节点补 error output / retry、执行数据保留策略）。每条一行：范围 + 建议 + 理由。没有就整区省略。

### 6. 行动区（排序）

| 顺序 | 动作 | 预期收益 |
|------|------|---------|

按"扣分权重 × 修复成本"排序，最多 5 条，只写能直接动手的动作（改哪个节点哪个字段），不写方向性建议。

## 写作纪律

- **每行信息自足**：位置、问题、修法在一行内闭环，读者不需要跳转其他章节找上下文
- **不写工作过程**：不贴原始 JSON/日志、不写检查方法——只给结论和证据锚点（执行 ID、字段路径）
- **术语统一**：节点名用工作流里的原名；维度名固定为「命名 / 参数 / 历史运行 / 业务编排」
- **报告头一行元信息**：工作流名、环境、样本量（评分时）、数据路径（MCP / 粘贴 JSON）
- 扣分项必须能回溯到总清单条目；给不出依据的，降级到提示区或不写
