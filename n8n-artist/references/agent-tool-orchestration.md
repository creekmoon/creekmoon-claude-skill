# 场景 E：Agent 工具编排（工具调用链设计）

Agent 节点的业务上下文（system prompt）和工具（tool）之间的调用关系是**设计出来的编排**，不是模型的自由发挥。工具链断在哪一环、每一环失败后怎么办，必须提前写在提示词和工具描述里——模型只会在你画的轨道上跑，轨道有缝，它就即兴发挥。

## E1. 工具调用链三问（设计时必答）

工具 A 的输出是工具 B 的输入时（如「先检索拿线索 → 再按线索取明细」），设计时必须回答：

1. **顺序与依赖**：先调谁、后调谁、B 依赖 A 的哪个输出。
2. **断链兜底**：A 返回空 / 失败时，B 的输入从哪来？必须给替代路径（见 E4），否则模型只能拿上下文瞎猜。
3. **每个环节的输入质量**：凡是让模型现场生成查询参数的（关键词、时间窗、ID），参数的 $fromAI 描述就是唯一的质量保障（见 E3）。

**三问的答案全部落在 Agent 节点的 system prompt**（骨架见 E8），不落在工具描述——编排逻辑是业务逻辑，集中在 prompt 一处维护，禁止下沉到各工具描述（见 E2）。

**链式依赖的设计底线**：链上每一步都要有独立价值，不能把下一步的输入完全押在第一步的命中率上。第一步的命中率受数据质量影响，不是必然事件——命中率高且稳定才允许串行；命中率不可控时，要么给下一步独立的输入路径（兜底写进 prompt），要么扇出并行调用让模型交叉验证。

反面信号：检索类工具 0 命中后，模型只能凭近期上下文猜查询条件，还容易被近期内容锚定在错误范围，换着花样猜都猜不中——数据明明存在，永远取不到。

## E2. 工具描述（toolDescription）规范：只写工具本身

工具描述的唯一职责是描述**这个工具本身**：它做什么、参数怎么填。它是工具的稳定契约——工具没变，描述就不该变。

**只写两类内容：**

- **工具能力**：一句话说清这个工具做什么、返回什么
- **参数指导**：每个参数的含义、格式、取值约束（与 $fromAI 描述配合）

**优先使用默认描述**：节点自带默认描述时（内置节点、自定义节点的官方描述），优先用默认的，不要覆盖。默认描述随节点版本维护，覆盖后只会腐化；只有默认描述有误导或缺失关键约束时才改写，且只补差异部分。

**禁止下沉到工具描述的内容**——编排逻辑属于 Agent 节点的 system prompt：

- 什么时候该调我（触发时机）→ 写进 system prompt
- 先调谁后调谁、和其他工具怎么配合 → 写进 system prompt
- 调用失败/未命中后的兜底链 → 写进 system prompt

为什么：工具间如何组合是**业务逻辑**，集中在 Agent prompt 一处，改流程只改一处；下沉到 N 个工具描述里会散落各处，改流程要同步改 N 处，且必然出现不一致。工具描述越"笨"，编排越可控。

反面信号：在工具描述里写"通常在「检索工具」拿到线索后调用""先调本工具，再调明细工具"——编排逻辑下沉，改流程要改 N 处描述且必然不一致。

反面信号：默认描述本身清晰可用，却整段覆盖成自定义文案——丢失随版本维护的官方描述，还引入了自己的措辞偏差。

## E3. $fromAI 参数三查

Agent 工具的参数多用 `$fromAI('参数名', '描述', '类型')` 让模型现场填值，逐项检查：

- **参数名达意**：`begin_time`、`keyword` 可以；自动生成的乱名（如 `_____Query_`）不行——乱名会显著增加模型输出畸形参数的概率，直接引发工具调用解析失败。
- **描述非空**：描述为空 = 模型没有任何输入指导，查询质量全凭运气。
- **约束写全**：参数间的逻辑约束必须写进描述（"必填"、"格式 yyyy-MM-dd"、"必须早于 end_time"），否则模型会漏传必填参数、传颠倒的区间——这两类都是执行中的高频报错。

## E4. 断链兜底路径（写进 system prompt）

必须为"第一步 0 命中/失败"写死升级路径，例如：

```
查询没有命中时，按顺序尝试：
1. 换同义词/上义词/相关词再查一次（最多 2 次）
2. 仍无命中：放宽过滤条件（更宽的时间窗/更少的关键词）再查
3. 仍未找到：如实告知用户没找到，并询问更具体的线索，不要编造
```

要点：

- 最后一步"允许说没找到"是信任关键——不写出来，模型就会编造；但要先穷尽检索再说没找到
- 每一步都要有硬上限（次数/范围），否则模型会无限检索烧 token
- 反面模式：「当前消息能答就不要调工具」这类一刀切的抑制规则，会把必须依赖检索才能回答的问题也压成直接回答

## E5. 检索覆盖缝隙检查（数据分层场景）

数据分层存储（原始数据 + 摘要/索引层）时，把每层支持的检索维度列出来，缝隙就是"数据存在但永远取不到"的来源：

| 层 | 检索维度 | 风险 |
|----|---------|------|
| 摘要/索引层 | 关键词/语义检索 | 摘要时原始词被改写丢失（专名、缩写、原话），关键词永远搜不到 |
| 原始数据层 | 仅按时间/ID 过滤 | 过滤条件靠模型猜，猜不中整段数据等于不存在 |

检查项：

- 摘要/索引的生成规则是否保留**可检索的原词**（专名、编号、原话）？
- 原始层是否只有单一过滤维度？关键字段应支持"关键词 + 时间"复合检索
- 工具链设计是否假设了"第一步必然命中"？

## E6. Agent 工具编排体检清单（并入场景 C）

- [ ] Agent 挂的多个工具**不重名**（同名工具直接执行报错 "multiple tools with the same name"）
- [ ] 每个 $fromAI 参数：参数名达意、描述非空、约束写全
- [ ] 工具描述只写工具本身与参数（优先默认描述，不整段覆盖）；触发时机、调用顺序、兜底链都在 system prompt 里，未下沉到工具描述
- [ ] system prompt 有断链兜底路径，且没有一刀切抑制工具调用的规则
- [ ] Agent 的 text 模板引用的字段（如 `{{ $json.messages }}`）在上游节点输出中真实存在——上游节点输出格式漂移会让 Agent **静默降级**（收不到数据却照答，答非所问）
- [ ] Agent 之后的下游节点若需要 webhook 原始上下文，表达式必须显式回指（如 `$('Webhook').first().json.body`）——Agent 输出 json 通常只剩 `{output}`，直接 `$json.xxx` 取不到上游字段

## E7. Agent 执行取证（从执行数据诊断工具调用行为）

体检 Agent 工作流时，执行数据按固定顺序读，每一步回答一个判断：

1. **Agent 调没调工具？** 看工具节点有没有执行记录。没执行 → 问题在触发时机（system prompt 没写清什么时候必须调）；有执行 → 往下看。
2. **工具入参是什么？** 看 $fromAI 参数实际解析出的值。为空/畸形/是乱名默认值 → 参数描述问题（回 E3 修）；入参合理但结果为空 → 往下看。
3. **工具返回几条？** `itemsOutput: 0` 就是 0 命中。注意一次执行里同一工具可能被调多次，执行数据里通常只保留最后一次调用——看到 0 命中时，先结合 Agent 最终回复里声称"查过哪里"，判断它实际查了几轮、每轮用的什么条件。
4. **Agent 回复声称的动作 vs 实际调用是否一致？** 回复说"查了 A 范围"，但执行里只有一次 B 范围的调用 → 模型在编造动作，或没把设计链路走完——说明 prompt 里的流程约束没生效。
5. **错误签名对照表**（Agent 工具编排的高发错误，按报错原文归类）：

| 报错原文特征 | 根因 | 修法 |
|-------------|------|------|
| `multiple tools with the same name` | 多个工具节点派生出同名工具 | 重命名工具节点，使工具名互不相同 |
| `缺少必填参数 xxx` | 模型没传必填参数，参数描述没强调必填 | 参数描述写明"必填"和格式 |
| 参数校验类报错（如区间颠倒） | 参数间逻辑约束没写进描述 | 约束写进 $fromAI 描述 |
| `Failed to parse tool arguments` | 参数名是乱名或 schema 太复杂，模型输出畸形 JSON | 参数名达意、精简参数个数 |
| 工具节点成功但 `itemsOutput: 0` | 查询 0 命中，链条断点 | 按 E4 补兜底，按 E5 查覆盖缝隙 |

## E8. 检索依赖型 Agent 的 system prompt 骨架（可直接复用）

适用于"Agent + 检索工具 + 明细拉取工具"的组合，把【】替换为实际工具名即可：

```
当问题依赖历史数据或外部数据、当前上下文里没有答案时，必须结合工具查证，不要凭近期上下文直接回答：
1. 先调【检索工具】：从用户问题里挑具体关键词（名称、编号、原话等）检索，拿到相关要点和定位线索。
2. 检索没有命中：换同义词、上义词或相关词再检索，最多再试 2 次。
3. 仍未命中：放宽条件（更宽的时间窗/更少的关键词）调【明细工具】直接扫描，最多查 N 个范围。
4. 拿到线索后调【明细工具】：圈定范围拉取明细，补齐上下文细节。
5. 结合两者组织回复：要点定方向，明细补细节；只依据工具返回的内容回答，不要编造。
6. 各种检索都试过仍没找到：如实告知没找到，请用户给一个更具体的线索，不要编造。

只有当问题完全依赖当前上下文就能回答时，才不调工具直接回复。
```

配套要点：

- 第 6 条是信任关键——允许模型说"没找到"，它才不会编造；但要先穷尽检索再说没找到
- "最多再试 2 次 / 查 N 个范围"的硬上限必须有，否则模型会无限检索烧 token
- 触发时机句要覆盖用户真实问法，从执行历史里收集实际问句来补全
- **套用骨架时的两条硬约束**：触发信号词列举只能增不能删（删一个，一类问题静默失触发）；把【】替换为实际工具名后，必须核对 prompt 中的工具引用名与节点名一致（工具名由节点名派生，改名不同步 = 模型按旧名找不到工具）
