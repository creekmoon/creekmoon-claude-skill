# 场景 C：异常体检（执行历史 + 失效引用 + 表达式健康）

工作流的"坏"分两种：**正在坏的**（执行在报错、结果不对）和**埋着雷的**（引用已失效，等特定数据进来才爆）。前者靠执行历史抓，后者靠静态检查抓。两条路径互为印证。

## C1. 执行历史体检（MCP 路径）

### 拉数据

1. `n8n_executions` `action='list'` + `workflowId`：取最近 50-100 次执行，统计成功率与错误率。
2. 加 `status='error'` 过滤，取最近几次失败：`action='get'` + `mode='error'` 看错误节点、错误消息、执行路径和上游采样数据。
3. 已激活的工作流：`n8n_get_workflow` 分别取 `mode='active'` 与默认草稿对比，确认草稿里的修复是否已发布。

### 分析维度

- **失败聚类**：失败集中在同一节点 → 该节点配置/凭据/上游契约问题，优先修；分散在各节点 → 多半是数据质量或外部系统波动。
- **错误消息分类**：鉴权失败（401/403）、超时、限流（429）、字段缺失、表达式求值错误——不同类别指向不同修法，报告里要分类汇总而不是罗列原始报错。
- **耗时趋势**：最近执行耗时是历史的数倍 → 数据量膨胀或某个节点在重试，提示排查。
- **成功率基线**：长期 100% 的工作流突然开始失败，哪怕失败率低也值得报告——通常是外部系统变更的前兆。

### 报告要求

执行历史部分输出：总执行数 / 成功率 / 失败节点 Top N / 错误分类汇总 / 耗时异常。每条结论附执行 ID 和时间，方便用户回溯。

> 工作流含 AI Agent 节点时，执行取证按 [agent-tool-orchestration.md](agent-tool-orchestration.md) 的 E7 五步法走：调没调工具 → 入参是什么 → 返回几条 → 声称 vs 实际 → 错误签名对照。

## C2. 失效引用静态检查（两条路径均可做）

失效引用是 n8n 最高频的 bug 源：上游节点改了名、删了字段、换了类型，下游表达式还指着旧世界。逐项检查：

### 四查失效引用

1. **引用不存在的节点**：正则扫全部节点 parameters 里的 `$node["X"]`、`$('X')`、`$node.X`，对照工作流节点名集合。X 不在集合中 → 失效（最常见诱因：节点重命名后表达式没同步）。
2. **引用 disabled 节点**：目标存在但 `disabled: true`——执行时该节点被跳过，引用拿到的是空或旧值。要么启用、要么改引用、要么删除引用段。
3. **孤儿连接**：`connections` 里作为 source key 或 target node 的名字不在节点列表中。MCP 路径可用 `n8n_autofix_workflow`（preview 模式）辅助确认，粘贴路径人工比对。
4. **字段级失效**（尽力推断，标注置信度）：`$node["X"].json.foo` 中的 `foo` 是否真的存在于 X 的输出——
   - X 是 Code 节点：读代码确认返回结构
   - X 是 Set/Edit Fields：看 fields 定义
   - X 是 HTTP Request 等外部节点：看 pinData 或执行历史采样；都没有就标「待运行验证」，不要硬下结论
   - 置信度写清楚：「确定失效」/「疑似失效」/「待验证」

### 表达式语法健康

- `{{ }}` 未闭合、括号不匹配
- 表达式里混进了纯文本（复制粘贴事故：`{{ $json.name }` 缺一个 `}`）
- 混用不兼容写法：旧版 `$node["X"].json` 与新版 `$('X').item.json` 在同一字段里拼接且没理清 item 对应关系

### 杂项异常

- **pinData 残留**：节点上钉着测试数据。上线前必须清除——pinData 会覆盖真实输入，测试数据进生产是经典事故。
- **空节点**：parameters 为空、无入向连接、无出向连接的节点，确认无用后建议删除。
- **矛盾配置**：`retryOnFail: true` 与 `continueOnFail: true` 同开（重试三次后继续假装成功，错误被吞）；`executeOnce`、`alwaysOutputData` 等影响执行语义的开关单独确认是否是有意为之。
- **外部节点无错误处理**：调外部 API 的节点既没开 retry、没接 error output、工作流也没挂 errorWorkflow——**仅作提示级建议，不纳入评分**（列入报告提示区）。

**Agent 节点的专项检查**（工具重名、$fromAI 参数质量、text 模板引用字段与上游输出契约、下游上下文丢失）见 [agent-tool-orchestration.md](agent-tool-orchestration.md) 的 E6 体检清单。

## C3. 失效引用的处置原则

失效 ≠ 无用。处置前先判断这个引用当初承载什么意图。**同类问题全量处理**：报错只是第一个露头，按模式枚举全部实例一次修完，不按报错逐个点名修。

| 情况 | 处置 |
|------|------|
| 引用的数据现在由新节点产出 | 重连：表达式改指新节点，报告里写明「旧来源 → 新来源」 |
| 该字段业务上已不需要 | 建议移除表达式段（或整个节点），移除前必须用户确认 |
| 拿不准是否还需要 | 列为「待确认」，给出验证方法（手动执行一次看上游输出 / 查看最近执行中该字段的实际值） |

**移除操作的输出**：变更清单逐项列「节点 → 位置（字段路径）→ 旧表达式 → 处置（移除/改指）→ 理由」，用户确认后才应用。修完后按同一模式全量复检（如全量搜索同类引用），不只验证改过的节点。

## C4. 体检报告模板

```markdown
# N8N 体检报告：<工作流名>

## 总评
🟡 近 7 天成功率 92%，2 个失效引用待处置

## 执行历史（近 100 次：成功 92 / 失败 8）
- 失败节点 Top: 「调用ERP接口」×6、「组装通知」×2
- 错误分类: 超时 ×5、401 鉴权 ×2、表达式求值错误 ×1
- ⚠️ 「调用ERP接口」近 3 次耗时从 2s 涨到 18s

## 必须修复
### [必须修复] 异常 · 失效引用
- 位置: 节点「组装通知」→ parameters.text
- 现象: `$node["旧订单查询"].json.orderNo` —— 节点「旧订单查询」不存在（疑似重命名）
- 置信度: 确定失效
- 处置: 建议改指「查询订单-按ID」；或确认字段废弃后移除

### [必须修复] 配置 · 矛盾开关
- 位置: 节点「调用ERP接口」
- 现象: retryOnFail 与 continueOnFail 同开，重试耗尽后错误被吞
- 处置: 二选一；关键流程建议关 continueOnFail 并接 error output

## 建议优化
### [建议优化] 异常 · pinData 残留
- 位置: 节点「Webhook」挂有 2 条 pinData，上线前应清除

## 待确认
- 节点「校验库存」引用 `$('查询商品').item.json.stock`，上游输出中未观测到该字段（近 10 次执行），疑似失效；建议手动执行一次验证
```
